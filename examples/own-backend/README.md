# Login with Link → your backend's session

This runnable Node.js example verifies the Link ID token, fetches the matching
profile and phone with the **Login user access token**, then issues independent
opaque access/refresh tokens for the application's API. No Link private key is
needed. This is the native public-client flow; code exchange remains in the
Swift/Kotlin SDK.

## Run from this SDK checkout

```sh
npm ci
npm run build
LINK_ISSUER='https://api-sdk.linkmessenger.me' \
LINK_API_BASE_URL='https://api-sdk-fr.linkmessenger.me' \
LINK_LOGIN_CLIENT_IDS='YOUR_IOS_LOGIN_CLIENT_ID,YOUR_ANDROID_LOGIN_CLIENT_ID' \
node examples/own-backend/server.mjs
```

Copy `issuer`, `api_base_url` and public Login client IDs from your Console
configuration. `issuer` and the regional API origin can differ. Only list this
backend's own clients; do not accept an issuer/client ID supplied by the caller.
The example listens on loopback port 8080 (`PORT` can override it).

## Native integration

1. Your app calls `POST /auth/link/challenge` with JSON `{}`. Save `challenge_id`
   in app memory (or secure pending-login storage if process recovery is needed).
   The response is `{ "challenge_id": "...", "nonce": "...", "expires_in": 300 }`.
2. Pass **that nonce** to a fresh native Login flow:

   ```swift
   let session = try await auth.signIn(
       scopes: ["openid", "profile", "phone"], nonce: challenge.nonce)
   // POST {challenge_id, id_token: session.idToken, access_token: session.accessToken}
   ```

   ```kotlin
   auth.signIn(listOf("openid", "profile", "phone"), opener, nonce = challenge.nonce).use { session ->
       // POST {challenge_id, id_token = session.idToken, access_token = session.accessToken}
   }
   ```

3. Send `challenge_id`, `id_token`, `access_token` to `POST /auth/link` over your
   HTTPS connection. No nonce in this request can override the saved value.
4. Use the returned **app** access token as `Authorization: Bearer app_at_...`
   for `GET /me`. Store the app refresh token in Keychain/Keystore. Rotate via
   `POST /auth/refresh` with `{ "refresh_token": "app_rt_..." }`.
5. `POST /auth/logout` with `{}` and the app access bearer revokes that app session.

The backend atomically consumes its five-minute challenge **before** verification.
The SDK checks Ed25519 signature, configured issuer/client, `azp`, times and the
expected nonce. It then fetches UserInfo with `expectedSub: identity.sub` and
requires `phoneNumber`. Accounts are mapped by verified `(issuer, sub)`, never
by mutable phone/name. State and PKCE remain independently generated by the
native SDK. Without a supplied nonce, native sign-in still generates its own.

Use the ID token from this fresh `signIn` result. A cached ID token belongs to
another attempt, and Link's refreshed ID tokens omit nonce. Neither can satisfy
a new backend challenge. If a Link SDK session already exists, deliberately
finish/sign out of it before starting another sign-in; `signIn` reports
`SessionExists`. After an ambiguous request failure, do not retry the same
challenge or consumed refresh token: start a new login. Serialize refreshes in
your client and persist the replacement token pair together.

`phone` must be approved for the project, enabled for the Login application,
requested in `signIn`, and granted by the user. If your product requires a phone,
configure it as required in Console too. A missing phone produces HTTP 403
`phone_required` and no app session in this example. The ID token does not contain
the phone. `phone_number_verified` is currently absent from Link UserInfo and
remains absent here; receiving a number does not create a verification claim.

Example successful response (token values abbreviated):

```json
{
  "token_type": "Bearer",
  "access_token": "app_at_...",
  "refresh_token": "app_rt_...",
  "expires_in": 900,
  "refresh_expires_in": 2592000,
  "user": {
    "id": "application-user-uuid",
    "name": "Alex",
    "preferred_username": "alex",
    "phone_number": "+12025550123"
  }
}
```

## Session/storage behavior

`auth.mjs` is the complete session example; `server.mjs` provides the HTTP routes.
Access tokens last 15 minutes. A refresh family expires 30 days after sign-in;
rotation does not extend that limit and invalidates the previous access token.
Reusing any consumed refresh revokes the entire family, including its newest
tokens. Only SHA-256 hashes of random app tokens are stored. Link tokens are
used for the initial exchange and are not retained. JSON responses use
`Cache-Control: no-store` and do not expose provider error bodies.

The bounded in-memory store is for a single local process: restarts erase
accounts, challenges and sessions. Before production, replace it with durable
storage with a unique `(issuer, sub)` account key, atomic one-use challenge
consumption and transactional refresh rotation/reuse revocation. Add HTTPS and
rate limits at the API edge. This example caps each store at 1,000 entries and
each family at 128 issued refresh tokens, after which a fresh login is required.
Do not enable request-body/Authorization logging for these endpoints.

Link disconnect/revocation does **not** automatically revoke your application's
already issued tokens. Define that policy separately (for example re-check Link
authorization for sensitive operations). UserInfo is fresh at sign-in; the
profile returned by this application's `/me` is an application snapshot.
